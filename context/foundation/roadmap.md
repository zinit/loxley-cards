# Roadmap: loxley-cards

> Derived from `context/foundation/prd.md` (v1) + auto-researched codebase baseline.
> Edit-in-place; archive when superseded.

## Vision recap

Gwint jest zablokowany wewnątrz Witchera 3 — nie istnieje lekka, webowa wersja tej mechaniki (rzędy, pogoda, best-of-3). Loxley-cards to standalone webowa karcianka inspirowana Gwintem: logowanie username + hasłem, partia vs bot (~15 min), kampania z progresją. Grupa docelowa: 1–10 osób, hobby-projekt budowany w 3 tygodnie wieczorami.

## North star

**S-03: Polished game UI** — gracz rozgrywa pełną partię best-of-3 vs prawdziwy bot w pięknym UI z S-01, podpiętym do REST API z S-02. Click-to-select kart, animacje, dynamiczne meta-tiles, end-of-round/match screens, lokalna persystencja unlocked stages. To walidacja głównej hipotezy produktu: czy silnik gry + UI grają razem jako produkt, nie jako prototyp.

> Gwiazda przewodnia — najmniejsza końcowa funkcjonalność, której dostarczenie udowadnia główną hipotezę produktu. Umieszczona w środku sekwencji (nie na początku), bo poprzedzające ją slice'y (S-01 statyczny UI z mock'iem, S-02 playable game API w prymitywnym debug UI) świadomie rozdzielają walidację wizualną od walidacji client-server — najpierw projektujemy UI z mock'iem, potem API z brzydkim frontem, S-03 łączy oba w spójną grę.

### F-06: AI code review pipeline

- **Outcome:** (foundation) AI code review na każdy PR — `.github/workflows/ai-review.yml` triggerowany na `pull_request: branches: [main]`, izolowany od F-05 `ci.yml` (osobny plik workflow, równoległe joby). Composable agent `.github/scripts/review.js` (Vercel AI SDK 6 + `@ai-sdk/anthropic` + Zod + `@octokit/rest`) wywołuje Claude Sonnet 4.6 z `temperature: 0` (deterministic verdict), `maxOutputTokens: 2000` (cap structured JSON), `maxRetries: 1` (cost discipline na network errors). Structured output (Zod schema): 5 kryteriów (correctness, idiomatic, complexity, tests, security) × score 1-10 + rationale, summary, verdict enum (APPROVED / NEEDS_ATTENTION / REJECTED). Conditional collapsibility: `<details>` dla APPROVED (compact), expanded dla NEEDS_ATTENTION/REJECTED. Diff size guard 50K znaków → skip + info komentarz "Diff too large for automated AI review". Workflow features: `concurrency: cancel-in-progress` (nowy push kanceluje aktualny job), `continue-on-error: true` na agent step (graceful failure — nie blokuje statusu PR), `permissions: contents:read + pull-requests:write` (least privilege). Diff delivery via temp file `/tmp/pr_diff.txt` (plan-review F1: `$GITHUB_ENV` ma limit ~48KB + ryzyko EOF delimiter collision). Trial PR test: 18s execution (znacznie poniżej NFR 2 min), APPROVED 10/10 we wszystkich kryteriach, wszystkie 3 checks zielone (`ai-review` + `CI/backend` + `CI/frontend` — guardrail "ci.yml UNTOUCHED + zero regresji F-05" empirycznie zweryfikowany).

### S-02: Playable game API (vertical slice)

- **Outcome:** backend wystawia 3 REST endpointy: `POST /games` (utwórz nową grę z deck'iem + zwróć initial GameState + legal moves), `GET /games/{id}` (pełen state + legal moves), `POST /games/{id}/moves` (waliduj + wykonaj ruch gracza + autoreply bota + zwróć new state + new legal moves). Nie ruszamy istniejącego ładnego UI z S-01. Wszystko lokalnie (`localhost:8080` + `localhost:5173`), bez deploymentu, bez auth. **Cel: udowodnić że client-server game flow działa end-to-end + zaprojektować kontrakt API zanim podpinamy ładne UI w S-03.**
